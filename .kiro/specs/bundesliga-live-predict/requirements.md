# Requirements Document

## Introduction

The **Live Predict** section is a new real-time mini-betting feature added to the public Bundesliga website frontend. It integrates natively into the existing site shell (navigation bar, header, footer) and lets users watch live Bundesliga matches and participate in short-lived mini-markets (12–60 seconds) generated automatically from official DFL tracking data. The section consists of three views: a live-matches listing, a live match detail with pitch visualisation and markets feed, and a personal bet history. A mock data layer replays a pre-recorded match simulation so the feature works without a connected backend; the mock is swappable for the real implementation by changing a single module flag. All UI strings are in German. A "DEMOMODUS" banner is always visible to make clear that no real money is involved.

---

## Glossary

- **Live_Predict_Section**: The new `/live-predict` area of the Bundesliga website, comprising all three views described in this document.
- **Match_Card**: A UI card component representing a single Bundesliga match, styled consistently with the existing `.match-card` pattern.
- **Mini_Market**: A short-lived betting market (12–60 s) generated by the backend trigger engine from DFL tracking events. Has 2–4 outcomes with decimal odds.
- **Outcome_Button**: A clickable UI element inside a Mini_Market card representing one possible outcome, showing label, decimal odds, and implied probability.
- **Pitch_View**: The SVG top-down football pitch visualisation showing real-time player and ball positions.
- **Markets_Feed**: The right-column vertical list of open Mini_Markets in the match detail view.
- **TTL**: Time-to-live — the remaining seconds before a Mini_Market closes and resolves.
- **Frame**: A WebSocket message type arriving at 25 Hz carrying the positions of 22 players and the ball.
- **KPI_Event**: A WebSocket message type carrying sporadic match events (goal, shot, foul, corner) with pre-calculated xG/xP values.
- **Mock_Layer**: A module that replays a pre-recorded `simulation_output.json` file, emitting the same message types as the real WebSocket backend.
- **Stream_Hook**: The `useMatchStream(matchId)` React hook that abstracts the WebSocket (or Mock_Layer) connection.
- **Bet_Slip**: The confirmation modal shown when a user clicks an Outcome_Button, containing an amount field and potential payout summary.
- **Meine_Wetten_Panel**: The panel below the two-column match detail layout listing the user's bets for the current match session.
- **History_View**: The `/live-predict/meine-wetten` page showing all historical bets in a table.
- **Design_System**: The set of CSS custom properties, typography rules, and visual patterns defined in the existing Bundesliga website template.
- **DEMOMODUS**: A persistent banner displayed in all Live Predict views indicating that no real money is involved.
- **i18n_Module**: The `i18n/de.ts` TypeScript module centralising all German UI strings.
- **Nav_Link**: A navigation item in the existing `.main-nav` bar.
- **LIVE_Pill**: A small red badge reading "LIVE" displayed next to the "Live Predict" Nav_Link when the section is active, and inside open Mini_Market cards.
- **Timeline**: A horizontal SVG bar below the Pitch_View spanning match minutes 0–90, with dots for key events and open markets.
- **Scoreboard**: The large score display at the top of the match detail left column, rendered in Oswald 56px.
- **Session_P_and_L**: The accumulated profit-and-loss figure for the user's bets within a single match session.

## Requirements

### Requirement 1: Navigation Integration

**User Story:** As a site visitor, I want to see a "Live Predict" link in the main navigation bar, so that I can access the Live Predict section without disrupting my existing browsing experience.

#### Acceptance Criteria

1. THE Live_Predict_Section SHALL add exactly one new Nav_Link with the text "Live Predict" to the existing `.main-nav` bar, positioned immediately after the "Liveticker" link.
2. THE Nav_Link SHALL navigate to the route `/live-predict` when clicked.
3. THE Nav_Link SHALL use the same visual style as all other `.nav-link` items: Roboto Condensed, 13px, font-weight 700, uppercase, letter-spacing 0.5px.
4. WHEN the current route begins with `/live-predict`, THE Nav_Link SHALL display a 3px Bundesliga red (`#d2001f`) underline to indicate the active state.
5. WHEN the current route begins with `/live-predict`, THE Nav_Link SHALL display a LIVE_Pill to the right of the "Live Predict" text with background `#d2001f`, font-size 9px, font-weight 700, padding 2px 6px, and border-radius 2px.
6. THE Live_Predict_Section SHALL NOT modify any existing Nav_Link, CSS rule, or HTML element outside the `.main-nav` insertion point.

---

### Requirement 2: Site Shell Preservation

**User Story:** As a site visitor, I want the existing header, navigation bar, and footer to remain unchanged when I navigate to Live Predict pages, so that the experience feels native to the Bundesliga website.

#### Acceptance Criteria

1. WHEN a user navigates to any `/live-predict` route, THE Live_Predict_Section SHALL render its content exclusively within the main content area, leaving the top-bar, `.main-nav`, and footer intact.
2. THE Live_Predict_Section SHALL apply only CSS custom properties already defined in the Design_System (`--red`, `--dark`, `--dark2`, `--dark3`, `--dark4`, `--border`, `--text`, `--text-muted`, `--text-dim`, `--espn-red`).
3. THE Live_Predict_Section SHALL NOT introduce Tailwind CSS, Material UI, or any third-party component library that overrides global styles.
4. THE Live_Predict_Section SHALL use CSS Modules or styled-components scoped to its own components to prevent style leakage into the existing site.

---

### Requirement 3: DEMOMODUS Banner

**User Story:** As a user, I want a clear indication that I am not betting real money, so that I am not misled about the nature of the platform.

#### Acceptance Criteria

1. WHILE a user is on any `/live-predict` route, THE Live_Predict_Section SHALL display a DEMOMODUS banner at the top of the content area, above all other Live Predict content.
2. THE DEMOMODUS banner SHALL contain the German text "DEMOMODUS – Keine echten Einsätze" in Roboto Condensed, 12px, uppercase.
3. THE DEMOMODUS banner SHALL remain visible at all times and SHALL NOT be dismissible by the user.
4. THE DEMOMODUS banner SHALL use background `--dark4` and text color `--text-muted` to remain visually discrete without obscuring match content.

---

### Requirement 4: Live Matches Listing View

**User Story:** As a user, I want to see all currently live Bundesliga matches on the `/live-predict` landing page, so that I can choose which match to follow and bet on.

#### Acceptance Criteria

1. WHEN a user navigates to `/live-predict`, THE Live_Predict_Section SHALL display a grid of Match_Cards for all matches whose status is `live` or `upcoming`.
2. EACH Match_Card SHALL display: home team logo (28×28 px), home team name, away team logo (28×28 px), away team name, current score, current match minute in Oswald 16px, and the count of currently open Mini_Markets as a red badge using `--red`.
3. WHEN a match status is `live`, THE Match_Card SHALL display a `.live-dot` (6×6 px red circle with `@keyframes blink` opacity 1→0.2 at 1s interval) adjacent to the match minute.
4. THE Live_Predict_Section SHALL refresh the list of live matches every 5 seconds by polling `GET /api/matches/live` (or the Mock_Layer equivalent).
5. WHEN no matches have status `live` or `upcoming`, THE Live_Predict_Section SHALL display an empty-state message in German ("Keine Live-Spiele verfügbar") and a list of the next scheduled matches.
6. WHEN a user clicks a Match_Card, THE Live_Predict_Section SHALL navigate to `/live-predict/:matchId` for the corresponding match.
7. WHEN a user hovers over a Match_Card, THE Match_Card SHALL apply `translateY(-2px)` transform and transition `border-color` to `--dark3`, with transition duration 150ms.
8. THE Match_Card SHALL use `cursor: pointer` when hovered.

---

### Requirement 5: Match Detail View — Layout

**User Story:** As a user, I want a two-column match detail page, so that I can watch the live pitch and interact with markets simultaneously.

#### Acceptance Criteria

1. WHEN a user navigates to `/live-predict/:matchId`, THE Live_Predict_Section SHALL render a two-column layout with the left column occupying approximately 60% of the content width and the right column approximately 40%.
2. THE left column SHALL contain, from top to bottom: the Scoreboard, the live metrics overlay, the Pitch_View SVG, and the Timeline.
3. THE right column SHALL contain, from top to bottom: the market filter pills and the Markets_Feed.
4. BELOW the two columns, THE Live_Predict_Section SHALL render the Meine_Wetten_Panel.
5. THE layout SHALL be responsive: WHEN the viewport width is below 900px, THE Live_Predict_Section SHALL stack the two columns vertically, left column above right column.

---

### Requirement 6: Scoreboard

**User Story:** As a user, I want to see the current score and match time prominently, so that I always know the match state at a glance.

#### Acceptance Criteria

1. THE Scoreboard SHALL display the home team name, current home score, a separator, current away score, and away team name.
2. THE Scoreboard SHALL render score digits in Oswald 56px, font-weight 300, consistent with a sports terminal style.
3. WHEN the match status is `live`, THE Scoreboard SHALL display the current match minute with a `.live-dot` adjacent to it.
4. WHEN a goal KPI_Event is received, THE Scoreboard SHALL update the score within 200ms of receiving the event.

---

### Requirement 7: Pitch View

**User Story:** As a user, I want to see a live top-down pitch visualisation with player and ball positions, so that I can follow the action and understand the context of each mini-market.

#### Acceptance Criteria

1. THE Pitch_View SHALL be rendered as an SVG element with a `--dark2` background and white pitch lines at 30% opacity.
2. THE Pitch_View SHALL represent each of the 22 players as a filled circle: home team players in Bundesliga red (`--red`), away team players in blue (`#1a6bb5` or equivalent), each with the player's jersey number in white text centred inside.
3. THE Pitch_View SHALL represent the ball as a smaller white filled circle.
4. WHEN a `frame` WebSocket message is received, THE Pitch_View SHALL update player and ball positions using `requestAnimationFrame` without triggering a React re-render of the component tree.
5. THE Live_Predict_Section SHALL store player and ball positions in a `useRef` value, not in React state, to prevent unnecessary re-renders.
6. THE Pitch_View SHALL sustain position updates at 25 Hz and maintain a rendering frame rate of at least 55 fps on a standard laptop.
7. THE Pitch_View SHALL smoothly interpolate player circle positions between received frames to avoid visual jitter.

---

### Requirement 8: Live Metrics Overlay

**User Story:** As a user, I want to see key live statistics above the pitch, so that I can make informed decisions when placing bets.

#### Acceptance Criteria

1. THE Live_Predict_Section SHALL display a metrics bar above the Pitch_View containing: possession percentage per team, accumulated xG per team, total shots per team, and the count of players currently sprinting (speed ≥ 25 km/h).
2. WHEN a KPI_Event or `frame` message updates a metric value, THE Live_Predict_Section SHALL update the corresponding metric display within 500ms.
3. THE metrics bar SHALL use Roboto Condensed 12px, `--text-muted` colour, uppercase labels.

---

### Requirement 9: Match Timeline

**User Story:** As a user, I want a visual timeline of match events below the pitch, so that I can understand the flow of the game and see when markets were triggered.

#### Acceptance Criteria

1. THE Timeline SHALL be rendered as an SVG bar spanning match minutes 0 to 90 (and extra time if applicable).
2. THE Timeline SHALL render a dot for each recorded KPI_Event: goals in green, shots in grey, corners in yellow, and open Mini_Markets in Bundesliga red (`--red`).
3. WHEN a user hovers over a Timeline dot, THE Live_Predict_Section SHALL display a tooltip containing the event type, match minute, and relevant detail (e.g., team name, xG value) in Roboto 12px.
4. WHEN a new KPI_Event is received, THE Timeline SHALL add the corresponding dot within 500ms.

---

### Requirement 10: Markets Feed

**User Story:** As a user, I want to see all currently open mini-markets in real time, so that I can quickly find and act on betting opportunities.

#### Acceptance Criteria

1. THE Markets_Feed SHALL display a vertical list of Mini_Market cards ordered by opening time, most recent first.
2. EACH Mini_Market card SHALL display: a blinking LIVE_Pill, a TTL countdown in Oswald monospace format "MM:SS" (e.g., "00:23"), the market question in Roboto 14px, and 2–4 Outcome_Buttons arranged side by side.
3. THE TTL countdown SHALL decrement every second and SHALL use `aria-live="polite"` so screen readers announce updates.
4. EACH Outcome_Button SHALL display: the outcome label, the decimal odds in Oswald 22px in `--red`, and the implied probability below the odds in Roboto 12px `--text-muted` (e.g., "p ≈ 46%").
5. WHEN a `market.new` WebSocket message is received, THE Markets_Feed SHALL prepend the new Mini_Market card to the top of the list within 200ms.
6. WHEN a `market.update` WebSocket message is received, THE Markets_Feed SHALL update the corresponding card's odds and TTL in place within 200ms.
7. WHEN a `market.settled` WebSocket message is received or the TTL reaches 0, THE Markets_Feed SHALL dim the card, display the winning outcome with a green checkmark and losing outcomes with a grey dash, then after 3 seconds slide the card into a collapsible historical feed section below the active markets.
8. THE Markets_Feed SHALL provide horizontal filter pills above the list with labels: "Alle", "Tor", "Torschuss", "Ecke", "Freistoß", "Sprint". Each pill SHALL display the count of currently open markets of that type.
9. WHEN a filter pill is selected, THE Markets_Feed SHALL show only Mini_Market cards matching the selected category.

---

### Requirement 11: Bet Placement

**User Story:** As a user, I want to place a bet on an outcome by clicking it and confirming in a modal, so that I can participate in mini-markets with a clear summary of my stake and potential payout.

#### Acceptance Criteria

1. WHEN a user clicks an Outcome_Button on an open Mini_Market card, THE Live_Predict_Section SHALL open a Bet_Slip modal.
2. THE Bet_Slip modal SHALL display: the market question, the selected outcome label, the decimal odds, an amount input field (numeric, minimum 1, maximum 500), and the calculated potential payout (amount × odds) updated in real time as the user types.
3. THE Bet_Slip modal SHALL contain a "Wette bestätigen" button and a "Abbrechen" button.
4. WHEN a user clicks "Wette bestätigen" with a valid amount, THE Live_Predict_Section SHALL submit a `POST /api/bets` request (or Mock_Layer equivalent) with the market ID, outcome ID, and amount.
5. IF the `POST /api/bets` request fails, THEN THE Live_Predict_Section SHALL display an inline German error message within the Bet_Slip modal without closing it.
6. WHEN a bet is successfully placed, THE Live_Predict_Section SHALL close the Bet_Slip modal and add the bet to the Meine_Wetten_Panel.
7. WHEN the TTL of a Mini_Market reaches 0 while the Bet_Slip modal is open for that market, THE Live_Predict_Section SHALL close the modal and display a German notification ("Markt abgelaufen – Wette nicht platziert").
8. EACH Outcome_Button SHALL have `role="button"`, an `aria-label` containing the market question, outcome label, and odds value, and SHALL be reachable and activatable via keyboard navigation.

---

### Requirement 12: Meine Wetten Panel

**User Story:** As a user, I want to see my bets for the current match session below the pitch and markets, so that I can track my activity and running P&L without leaving the match view.

#### Acceptance Criteria

1. THE Meine_Wetten_Panel SHALL display a list of all bets placed by the user during the current match session, each showing: market question, chosen outcome, stake amount, decimal odds, status (ausstehend / gewonnen / verloren), and return amount.
2. THE Meine_Wetten_Panel SHALL display the Session_P_and_L (net profit/loss) as a summary figure above the bet list, updated whenever a bet settles.
3. WHEN a Mini_Market settles and the user has a bet on it, THE Meine_Wetten_Panel SHALL update the bet status and return amount within 500ms of receiving the `market.settled` message.
4. WHEN the user has placed no bets in the current session, THE Meine_Wetten_Panel SHALL display the German text "Noch keine Wetten in diesem Spiel".

---

### Requirement 13: History View

**User Story:** As a user, I want to review all my past bets across all matches, so that I can analyse my performance over time.

#### Acceptance Criteria

1. WHEN a user navigates to `/live-predict/meine-wetten`, THE Live_Predict_Section SHALL display a table styled consistently with the existing `.standings-table` pattern.
2. THE table SHALL include columns: Datum, Spiel, Markt, Gewähltes Ergebnis, Einsatz, Quote, Status, Rückgabe.
3. THE History_View SHALL display a summary row above the table showing: total wagered, total won, net P&L, and hit rate (percentage of winning bets).
4. THE History_View SHALL provide filter controls for status (Alle / Gewonnen / Verloren / Ausstehend) and match (dropdown of all matches with bets).
5. WHEN a filter is changed, THE History_View SHALL update the displayed rows and summary figures within 200ms without a full page reload.

---

### Requirement 14: Real-Time Data Stream

**User Story:** As a developer, I want a single abstracted hook for the WebSocket stream, so that components can consume live data without coupling to the transport layer.

#### Acceptance Criteria

1. THE Stream_Hook (`useMatchStream(matchId)`) SHALL connect to `wss://api/live/:matchId` and expose callbacks or state for `frame`, `event`, `market.new`, `market.update`, and `market.settled` message types.
2. WHEN the WebSocket connection is lost, THE Stream_Hook SHALL attempt to reconnect with exponential back-off, up to a maximum of 5 retries.
3. IF reconnection fails after 5 retries, THEN THE Stream_Hook SHALL set a connection error state that the consuming component can display to the user in German ("Verbindung unterbrochen – bitte Seite neu laden").
4. THE Stream_Hook SHALL accept a `matchId` parameter and SHALL NOT mix messages from different matches.
5. WHEN the component using THE Stream_Hook unmounts, THE Stream_Hook SHALL close the WebSocket connection and cancel any pending reconnection timers.

---

### Requirement 15: Mock Data Layer

**User Story:** As a developer, I want a mock data layer that replays a pre-recorded match simulation, so that the frontend can be developed and demonstrated without a live backend.

#### Acceptance Criteria

1. THE Mock_Layer SHALL replay the `simulation_output.json` file, emitting `frame`, `event`, `market.new`, `market.update`, and `market.settled` messages at the same cadence as the real backend (25 Hz for frames, event-driven for others).
2. THE Mock_Layer SHALL implement the same interface as the real WebSocket transport so that THE Stream_Hook requires no changes to switch between mock and real modes.
3. THE Live_Predict_Section SHALL switch between Mock_Layer and real WebSocket transport by changing a single boolean flag in a configuration module (e.g., `config/dataSource.ts`).
4. THE Mock_Layer SHALL also provide mock responses for `GET /api/matches/live`, `GET /api/matches/:id`, and `POST /api/bets` with data consistent with the replayed match.
5. WHEN the mock replay reaches the end of the `simulation_output.json` data, THE Mock_Layer SHALL loop back to the beginning seamlessly.

---

### Requirement 16: Performance Budget

**User Story:** As a user, I want the Live Predict section to load quickly and run smoothly, so that I can follow fast-paced match events without lag or jank.

#### Acceptance Criteria

1. THE Live_Predict_Section initial JavaScript bundle SHALL be no larger than 200 KB when gzip-compressed.
2. THE Pitch_View SHALL maintain a rendering frame rate of at least 55 fps while processing 25 Hz `frame` messages on a standard laptop (defined as a machine with a mid-range CPU, e.g., Intel Core i5 8th gen or equivalent).
3. THE Live_Predict_Section SHALL NOT trigger a React component tree re-render for each incoming `frame` message; position updates SHALL be applied directly to the SVG DOM via `requestAnimationFrame`.
4. THE Live_Predict_Section SHALL use React code-splitting (dynamic `import()`) to load the match detail view only when the user navigates to `/live-predict/:matchId`.

---

### Requirement 17: Accessibility

**User Story:** As a user with assistive technology, I want the Live Predict section to be keyboard-navigable and screen-reader-friendly, so that I can participate in markets without relying solely on a mouse.

#### Acceptance Criteria

1. EACH Outcome_Button SHALL be reachable via Tab key navigation and activatable via Enter or Space key.
2. EACH Mini_Market card's TTL countdown SHALL use `aria-live="polite"` so that screen readers announce time updates without interrupting other announcements.
3. THE Bet_Slip modal SHALL trap keyboard focus within the modal while it is open and return focus to the triggering Outcome_Button when closed.
4. THE Pitch_View SVG SHALL include an `aria-label` describing the current match and a `role="img"` attribute; individual player circles SHALL NOT be individually focusable (they are decorative).
5. THE Live_Predict_Section SHALL provide visible focus indicators on all interactive elements, using an outline consistent with the Design_System (e.g., `2px solid var(--red)`).

---

### Requirement 18: Internationalisation

**User Story:** As a developer, I want all UI strings centralised in a German language module, so that adding English or Spanish translations later requires no changes to component code.

#### Acceptance Criteria

1. THE i18n_Module (`i18n/de.ts`) SHALL export a typed object containing every user-visible string used in the Live_Predict_Section.
2. THE Live_Predict_Section SHALL NOT contain hard-coded German strings in component JSX or TypeScript files; all strings SHALL be imported from THE i18n_Module.
3. THE i18n_Module SHALL be structured so that adding a new locale requires only creating a parallel file (e.g., `i18n/en.ts`) with the same exported keys.

---

### Requirement 19: Tech Stack and Project Structure

**User Story:** As a developer, I want the Live Predict section built with the agreed tech stack, so that it integrates cleanly with the existing codebase and team conventions.

#### Acceptance Criteria

1. THE Live_Predict_Section SHALL be implemented in React 18+ with TypeScript in strict mode, bundled with Vite.
2. THE Live_Predict_Section SHALL use React Router v6 to define the routes `/live-predict`, `/live-predict/:matchId`, and `/live-predict/meine-wetten`.
3. THE Live_Predict_Section SHALL use Zustand for global state management covering: authenticated user session, list of open markets, and the user's placed bets. Redux SHALL NOT be used.
4. THE Live_Predict_Section SHALL define TypeScript interfaces for all backend DTOs (match metadata, frame message, KPI event, market, bet) in a dedicated `types/` directory.
5. THE Live_Predict_Section SHALL include Vitest and React Testing Library as test dependencies, with unit tests covering: Mini_Market card rendering and TTL countdown, Stream_Hook reconnection logic, market settlement and card transition, and Bet_Slip amount validation and payout calculation.

---

### Requirement 20: Parser and Serialiser Round-Trip

**User Story:** As a developer, I want the JSON message parsing to be reliable and verifiable, so that malformed or unexpected backend messages do not cause silent data corruption.

#### Acceptance Criteria

1. THE Live_Predict_Section SHALL define a parser for each WebSocket message type (`frame`, `event`, `market.new`, `market.update`, `market.settled`) that validates the message structure and returns a typed DTO or a descriptive parse error.
2. IF a received WebSocket message fails validation, THEN THE Live_Predict_Section SHALL log the error to the console and discard the message without crashing.
3. THE Live_Predict_Section SHALL include a pretty-printer function for each DTO type that serialises the typed object back to a JSON-compatible plain object.
4. FOR ALL valid DTO objects, parsing the JSON output of the pretty-printer SHALL produce an equivalent DTO object (round-trip property). This SHALL be verified by property-based tests using Vitest.
